# Research: CI secrets / Doppler provisioning for the e2e runner

**Date:** 2026-09-04
**Question (issue [#235](https://github.com/Virtality-app/virtality-platform/issues/235)):** Does a Doppler CI service token already exist for GitHub Actions? What's the minimal secret set the Playwright e2e job needs (Stripe test key, a way to create Access Code/Tester Code/Coupon fixtures, preview base URL(s))? How should it be provisioned — Doppler CI service token vs plain GitHub Actions secrets?
**Audience:** Whoever builds [#239](https://github.com/Virtality-app/virtality-platform/issues/239) (CI workflow: e2e against preview) and [#237](https://github.com/Virtality-app/virtality-platform/issues/237) (fixture-creation harness design). Child of wayfinder map [#227](https://github.com/Virtality-app/virtality-platform/issues/227).
**Scope:** Primary sources only — repo files, `gh` CLI against the live GitHub API, and Doppler's own docs at docs.doppler.com.

---

## 1. Does a Doppler CI service token already exist for GitHub Actions?

**No.** Confirmed from four angles:

1. **Repo-level secrets.** `gh secret list --repo Virtality-app/virtality-platform` returns exactly 7 secrets: `PRODUCTION_DATABASE_URL`, `STAGING_DATABASE_URL`, `VERCEL_PROJECT_ID_CONSOLE`, `VERCEL_TOKEN`, `VPS_HOST`, `VPS_SSH_KEY`, `VPS_USER`. No `DOPPLER_TOKEN` or similarly named secret.
2. **Environment-level secrets.** The repo has 4 GitHub Environments matching the preview deploy targets: `Preview – vir-console`, `Preview – vir-server`, `Preview – vir-admin`, `Preview – vir-website` (from `gh api repos/Virtality-app/virtality-platform/environments`, all created 2026-02-24/28). Running `gh secret list --repo Virtality-app/virtality-platform --env "<name>"` for all four (en dash `–`, quoted) returns **empty** for every one — no secrets configured at the environment level either.
3. **No workflow references Doppler.** `grep -rniE "doppler" .github/` returns nothing. The 3 existing workflows (`.github/workflows/deploy-server-preview.yml`, `deploy-server-production.yml`, `prisma-migrate-deploy.yml`) contain no `dopplerhq/cli-action`, no `doppler run`, and no Doppler-related step.
4. **No GitHub App config.** There is no `.github/` app manifest or any repo-visible marker of a Doppler GitHub App installation (the Doppler↔GitHub sync integration authorizes at the org/installation level and leaves no trace in repo files — this can only be confirmed/denied from the GitHub org's Installed GitHub Apps page or the Doppler dashboard's Integrations tab, neither of which this research had access to check; the _repo-visible_ evidence — no synced secrets appearing in any environment or repo secret list — is consistent with "not installed for this repo").

**What CI Doppler provisioning would look like if adopted**, per Doppler's own docs:

- **Doppler↔GitHub sync integration** (https://docs.doppler.com/docs/github-actions): authorize the "Doppler GitHub Application" against the repo, pick a GitHub feature to sync into (Actions secrets, Codespaces, Dependabot, or Copilot Agents), pick the source Doppler project+config. From then on, "every time you add, update or remove a secret in Doppler, that change will be instantly reflected in the GitHub secrets." This is push-based and one-way — "Doppler cannot import existing secrets or sync changes to secrets made in GitHub as the secret values are hidden" (same page). Net effect: it _populates_ ordinary `secrets.<NAME>` GitHub Actions secrets for you; workflow YAML is unchanged (`secrets.STRIPE_SECRET_KEY` etc., same as today).
- **Direct CLI approach** (https://docs.doppler.com/docs/service-tokens): create a config-scoped service token — `doppler configs tokens create --project virtality-platform-server --config stg my-ci-token --plain` (or via dashboard: project config → Access tab → Generate) — scoped to exactly one project + one config ("adheres to the principle of least privilege by ensuring an application only has access to a single config within a project"). Store the resulting `dp.st.stg.xxxx` value as a single GitHub secret, conventionally `DOPPLER_TOKEN`. In the workflow, install the Doppler CLI (e.g. `dopplerhq/cli-action`) and wrap the test command: `doppler run -- pnpm test:e2e`, with `DOPPLER_TOKEN: ${{ secrets.DOPPLER_TOKEN }}` in the step env. This is the pattern already used for local dev (`doppler run --`) and documented as a deliberate follow-up in `docs/onboarding/doppler.md:369`: "Sync `stg`/`prd` to Vercel / GitHub Actions via Doppler integrations + service tokens" — listed under "Follow-ups (not required for local `dev`)" (`docs/onboarding/doppler.md:366`), i.e. explicitly **not yet done**.

Either Doppler path is additive and does not require re-architecting the two secrets the e2e job needs (§2) — both still resolve to ordinary env vars or GitHub secrets by the time the job runs.

## 2. Minimal secret set for the e2e job

### 2a. Stripe test-mode secret key

`services/server/.env.example:24,27` lists `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` both commented out (optional locally, no value committed). The e2e suite needs a **test-mode** `STRIPE_SECRET_KEY` only if Playwright/test setup calls the Stripe test-mode API directly (e.g. to construct or verify state around Checkout) — Decision [#232](https://github.com/Virtality-app/virtality-platform/issues/232) ("Stripe sandbox webhook handling per environment") establishes preview already has a live webhook endpoint wired to its own Stripe keys server-side, so the _server's_ Stripe key is already provisioned wherever preview's app secrets live (not visible in this repo — VPS-side per `~/infra/scripts/infra.sh server-preview-up`, and Vercel-side for console via its own env vars, neither inspectable via `gh`). What's still needed is a **separate** test-mode key available _to the CI runner process itself_, scoped read/write to the same Stripe sandbox, only if the fixture/assertion code calls Stripe directly rather than solely through the app under test. This is one secret either way: `STRIPE_SECRET_KEY` (test mode).

### 2b. Access Code / Tester Code / Coupon fixture creation — HTTP over raw DB access

Per Decision [#231](https://github.com/Virtality-app/virtality-platform/issues/231), fixtures are created by calling orpc procedures directly, not adminboard UI automation or DB seeding. Checked whether that means "in-process Node script holding `DATABASE_URL`" or "HTTP call against a preview API endpoint":

- **orpc procedures are already exposed over HTTP.** `packages/orpc/src/orpc-handler.ts:1,5` wraps the full `router` in an `@orpc/server/fetch` `RPCHandler`. `services/server/src/middleware/orpc.ts:9-21` mounts it in the Hono app: `orpcHandler.handle(c.req.raw, { prefix: ORPC_PREFIX, context: { prisma, headers, request, user, session, s3, revalidateWebsiteMarketingCache } })`. `ORPC_PREFIX` resolves to `/api/v1/rpc` (`packages/shared/src/types/general.ts:3-4`, `API_PREFIX = '/api/${API_VERSION}'`, `ORPC_PREFIX = '${API_PREFIX}/rpc'`). `packages/orpc/src/client.ts` provides `createORPCClient` built on `@orpc/client`'s `RPCLink` (a fetch-based link), i.e. the same client shape usable from a Node test-setup script hitting a URL, not just from the Next.js apps in-process.
- **But every fixture procedure requires an authenticated session, not raw DB creds.** `packages/orpc/src/procedures/console-access-code.ts`, `tester-code.ts`, and `coupon-library.ts` are all built on the `authed` middleware (`packages/orpc/src/middleware/auth.ts:8-20`): `requireAuth` throws `ORPCError('UNAUTHORIZED')` unless `context.user` and `context.session` are present, and those are only populated when Hono's auth layer resolves a real Better Auth session from the request (`context.user: c.var.user, context.session: c.var.session` in `orpc.ts:16-17`). So calling these procedures over HTTP needs a valid session cookie/token, not a bearer secret — there is no service-account/API-key bypass for orpc procedures visible in `packages/orpc/src/middleware/auth.ts`.
- **Better Auth supports email/password login**, which is how a test runner would obtain that session over HTTP without touching Postgres: `packages/auth/src/auth-instance.ts:155` configures `emailAndPassword`, and `:194-195` registers the `admin({ ac, roles })` plugin (role-based access control), meaning a seeded test admin/service account with email+password credentials could authenticate through Better Auth's own HTTP API, then reuse that session's cookie for orpc calls — including calling `tester-code.ts`'s `create`/`delete` (`packages/orpc/src/procedures/tester-code.ts:16-46,58-66`), which have no additional per-procedure privilege check beyond `authed`.
- **Conclusion — the lower-privilege option is available and should be used.** The e2e runner does **not** need a raw preview `DATABASE_URL` to create these fixtures. It needs: (1) the preview server's base URL, and (2) credentials for one seeded test account (with sufficient role for `tester-code`/`coupon-library`/`console-access-code` procedures) able to authenticate via Better Auth's HTTP API and then call the existing `/api/v1/rpc/*` HTTP endpoints through `createORPCClient`. That's a test-account email + password (2 small secrets, or one combined), not a database connection string — meaningfully lower blast radius than handing CI the same `STAGING_DATABASE_URL` already used for migrations. Exact seeding of that test account (who creates it, what role, whether it's a one-time manual Doppler/DB step or scripted) is unresolved and belongs to [#237](https://github.com/Virtality-app/virtality-platform/issues/237) ("Design fixture-creation harness"), not this ticket.

### 2c. Preview base URL(s)

Playwright needs a `baseURL` for console (`apps/console`, deployed via Vercel native git integration per Decision #230) and the fixture-creation script needs the server's base URL (`services/server`, deployed to the VPS per `.github/workflows/deploy-server-preview.yml`). Checked the repo for anything resolving either automatically:

- No `vercel.json` in the repo.
- No deploy-hook URL, alias, or fixed preview domain referenced anywhere (`grep` across the repo for `deploy-hook`/`vercel.com/.../deploy-hooks` and similar turned up nothing).
- `.github/workflows/deploy-server-preview.yml` deploys by SSH + `docker pull ... :preview` tag + `~/infra/scripts/infra.sh server-preview-up` on the VPS — no URL is emitted back to GitHub Actions as an output.
- Console's preview URL is whatever Vercel's git-integration bot comments on the PR (dynamic per-deploy alias unless a fixed preview domain/alias is configured in the Vercel project) — nothing in-repo pins it.

**This preview-base-URL / deploy-hook resolution mechanism does not exist yet in this repo.** It is, however, **already its own ticket**: [#236](https://github.com/Virtality-app/virtality-platform/issues/236), "Research: Vercel deployment hook → GitHub Actions wiring," open and unblocked. So this is not an unticketed gap — see the flag in the final section below for why #235 and #236 need to land in a compatible order.

## 3. Recommendation: plain GitHub Actions secrets, not a Doppler CI service token — for now

**Recommendation: provision the e2e job's 2-3 secrets as plain GitHub Actions secrets (repo-level or on the relevant `Preview – vir-*` Environments), the same way `prisma-migrate-deploy.yml` and `deploy-server-preview.yml` already do it. Do not introduce a Doppler↔CI integration as part of this ticket.**

Reasoning:

- **(i) Doppler-for-local-dev investment doesn't transfer much value to CI yet.** The team already has `doppler.yaml` mapping `services/server` and `apps/console` (among others) to `virtality-platform-server`/`virtality-platform-console` projects with `dev`/`stg`/`prd` configs (`doppler.yaml:7-9,16-18`), so the _secret organization_ already exists in Doppler. But the e2e job is a consumer of at most 2-3 values (a Stripe test key, a test-account email/password, and — pending #236 — a base URL), not a full app process that needs the rest of `stg`'s secret set. A Doppler service token buys "one secret to rotate" at the cost of standing up a new integration (GitHub App auth or a service-token-secret + `dopplerhq/cli-action` step) for a job that would otherwise need 2-3 GitHub secrets anyway.
- **(ii) Existing CI precedent is 100% plain GitHub secrets.** Every workflow that consumes a secret in this repo today — `prisma-migrate-deploy.yml` (`secrets.STAGING_DATABASE_URL`, `secrets.PRODUCTION_DATABASE_URL`) and `deploy-server-preview.yml`/`deploy-server-production.yml` (`secrets.GITHUB_TOKEN`, VPS secrets) — uses `secrets.<NAME>` directly with zero Doppler involvement. Following that precedent is the path of least resistance and keeps CI's secret-handling story uniform (one mental model, one place to look for CI credentials) rather than forking it per-workflow.
- **(iii) The math doesn't favor Doppler yet.** `docs/onboarding/doppler.md:366-369` already lists "Sync stg/prd to Vercel / GitHub Actions via Doppler integrations + service tokens" as a deferred follow-up, not a blocking gap — it was written knowing CI wasn't using Doppler and treating that as fine for now. Introducing Doppler to CI is worth it once there's a real accumulation of CI secrets across multiple workflows/environments (rotation becomes painful, or `stg`/`prd` drift between Doppler and GitHub secrets becomes a real risk). At 2-3 secrets for one new job, that threshold isn't met — plain GitHub Environment secrets on the `Preview – vir-console` / `Preview – vir-server` environments (already provisioned and currently empty, confirmed in §1.2) are simpler to set up, audit, and reason about today.

**Tradeoff to flag honestly:** this creates a second source of truth for `STRIPE_SECRET_KEY` (test mode) if Doppler's `virtality-platform-server` `stg` config also holds a Stripe key for local `doppler run` against staging — the GitHub secret and the Doppler value must be kept in sync by hand, or deliberately allowed to be different values (a CI-only Stripe test key vs. a shared staging one) if that's the safer default. Revisit the Doppler-for-CI follow-up once more workflows need secrets (e.g. if #239's e2e job is joined by other preview-gated jobs), at which point the sync-integration path (§1) is strictly additive on top of `doppler.yaml`'s existing project structure and requires no workflow rewrite.
