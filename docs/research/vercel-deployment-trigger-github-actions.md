# Research: Triggering GitHub Actions once a Vercel + server preview are both live

**Date:** 2026-09
**Question:** Once `apps/console`'s Vercel preview deployment and `services/server`'s preview deploy (via `.github/workflows/deploy-server-preview.yml`) have both finished for the same commit pushed to `dev`, what is the simplest, most reliable mechanism to trigger the future e2e GitHub Actions workflow (tracked as issue #239)?
**Audience:** Whoever implements #239/#227; assumes familiarity with GitHub Actions and this repo's `deploy-server-preview.yml`.
**Scope:** GitHub's `deployment_status`, `workflow_run`, and `repository_dispatch` triggers; Vercel's native GitHub integration, Deploy Hooks, project/account webhooks, and REST API; how they combine (or don't) for a two-piece preview environment on `dev`.
**Sources:** [vercel.com/docs](https://vercel.com/docs) and [docs.github.com](https://docs.github.com) pages, cited inline. Verified 2026-09-04.

---

## 1. Does Vercel's native GitHub integration create GitHub Deployments and fire `deployment_status`?

Yes. Vercel for GitHub (the dashboard-configured, no-`vercel.json` integration this repo uses for `apps/console`) has **`Deployments` read/write permission on the GitHub App** specifically "to synchronize deployment status between GitHub and the Vercel infrastructure," and the docs state directly: "By default, Vercel notifies GitHub of deployments using [the `deployment_status` webhook event]" ([Deploying GitHub Projects with Vercel](https://vercel.com/docs/git/vercel-for-github)). This is a real GitHub Deployment (Deployments API), not just a commit status — the same page notes "you will also be able to integrate with other services through [GitHub's checks]" because it uses the Deployments API.

**Environment value and payload fields.** The GitHub `deployment_status` webhook payload nests `environment` and `sha` under `deployment`, and `state`/`target_url` under `deployment_status` ([Webhook events and payloads — deployment_status](https://docs.github.com/en/webhooks/webhook-events-and-payloads#deployment_status)). Vercel's own migration example confirms the exact fields to check in a workflow: `github.event.deployment_status.state == 'success'` and `github.event.deployment_status.environment_url` for the URL ([Deploying GitHub Projects with Vercel — Migrating from `deployment_status`](https://vercel.com/docs/git/vercel-for-github#migrating-from-deployment_status)). The docs do not publish the exact string used for `environment` (e.g. whether it is literally `"Preview"`); it must be read off an actual event or the GitHub UI rather than assumed.

**Fires on every branch push, not just PRs.** "Vercel for GitHub will **deploy every push by default**. This includes pushes and pull requests made to branches" ([Deploying GitHub Projects with Vercel — A Deployment for Each Push](https://vercel.com/docs/git/vercel-for-github#a-deployment-for-each-push)), and separately: "Preview: deploying for further testing... By default, Vercel creates a preview deployment when you: Push a commit to a branch that is **not** your production branch" ([Environments](https://vercel.com/docs/deployments/environments)). So a push to `dev` (assuming `dev` isn't the production branch) gets a Preview deployment and, per the above, a `deployment_status` event — the same mechanism PRs use.

**Gotchas, per GitHub's own docs and Vercel's:**

- `deployment_status`-triggered workflows only run if the workflow file exists **on the default branch** — this is a general GitHub Actions restriction on every event type covered here ([Events that trigger workflows](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows)).
- "When a deployment status's state is set to `inactive`, a workflow run will not be triggered" (same page) — not a concern here since we'd filter on `state == 'success'` anyway.
- Vercel explicitly steers new integrations away from this event: **"we encourage migrating to `repository_dispatch` events"** (see §2) and ships a UI toggle to disable `deployment_status` events entirely per-project ([Silence deployment notifications on pull requests](https://vercel.com/docs/git/vercel-for-github#silence-deployment-notifications-on-pull-requests)) — i.e. Vercel considers `deployment_status` the legacy path, not the recommended one, for exactly this workflow-trigger use case.

## 2. Deploy Hooks vs. outgoing webhooks vs. Vercel's built-in `repository_dispatch`

**Deploy Hooks are inbound-only — ruled out.** "Deploy Hooks allow you to create URLs that accept HTTP `POST` requests **in order to trigger deployments**... These URLs are uniquely linked to your project, repository, and branch" ([Creating & Triggering Deploy Hooks](https://vercel.com/docs/deploy-hooks)). They start a deployment; they carry no information about a deployment finishing, and there is no request/response signal usable to gate a downstream workflow. Not applicable to "wait for a deploy to finish."

**Vercel account/project webhooks are outbound but generic and gated by plan.** Configurable webhooks (Settings → Webhooks) support `Deployment Succeeded`/`Deployment Error`/etc., but are explicitly scoped to paid tiers: **"Pro and Enterprise teams will be able to configure these webhooks at the account level"** ([Setting Up Webhooks — Account Webhooks](https://vercel.com/docs/webhooks#account-webhooks)). The payload is a generic `{id, type, createdAt, payload, region}` envelope, and — critically — Vercel's webhook endpoint is one-way HTTP POST to whatever URL you configure; it cannot itself authenticate to and call GitHub's `repository_dispatch` API (`POST /repos/{owner}/{repo}/dispatches`, which needs a `repo`-scoped token in an `Authorization` header — [Repos API — create a repository dispatch event](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28#create-a-repository-dispatch-event)). Using this path would require standing up a small relay (e.g. a Vercel serverless function or Lambda) whose only job is to receive the webhook and re-POST to GitHub with a stored PAT — genuinely new infrastructure this team doesn't have.

**But Vercel already ships this relay for you, built into the native GitHub integration.** Separately from the generic account webhooks above, the _Vercel for GitHub_ integration itself can send `repository_dispatch` events directly to the connected repo — no intermediary needed:

> "Vercel sends `repository_dispatch` events to GitHub when the status of your deployment changes. These events can trigger GitHub Actions... GitHub Actions can trigger on the following events: `vercel.deployment.ready`, `vercel.deployment.success`, `vercel.deployment.error`, `vercel.deployment.canceled`, `vercel.deployment.ignored`, `vercel.deployment.skipped`, `vercel.deployment.pending`, `vercel.deployment.failed`, `vercel.deployment.promoted`"
> ([Deploying GitHub Projects with Vercel — Repository dispatch events](https://vercel.com/docs/git/vercel-for-github#repository-dispatch-events))

The `client_payload` carries deployment `id`, `environment`, `url`, git `ref`/`sha`, and project `id`/`name` (per the type definitions Vercel links from that section, [`vercel/repository-dispatch`](https://github.com/vercel/repository-dispatch)), so a workflow can check `github.event.client_payload.git.sha` (or `.sha`) against the commit it cares about and read `github.event.client_payload.url` for the live preview URL directly — no polling. Vercel's own worked example for this exact scenario (running e2e tests after a preview deploy) uses `repository_dispatch: types: ['vercel.deployment.success']` in place of `deployment_status` ([How can I run end-to-end tests after my Vercel Preview Deployment?](https://vercel.com/kb/guide/how-can-i-run-end-to-end-tests-after-my-vercel-preview-deployment)), including a note that if Deployment Protection is on, "Protection Bypass for Automation" must be configured so the test runner can reach the preview.

**Complexity comparison.** Vercel's native `repository_dispatch` (call it **option C**) needs zero extra infrastructure beyond the git integration this repo already has — same footprint as option A (native `deployment_status`), but richer, targeted payload (exact commit SHA + ready URL in the event itself, no need to separately query state/environment) and is the path Vercel's own docs actively steer integrators toward. Option B (generic account webhook → custom relay → `repository_dispatch`) is strictly more work for no benefit here and should be dropped. Vercel's public docs do not state a plan-tier restriction on the native integration's `repository_dispatch` events (unlike the Pro/Enterprise-gated account webhooks), so it should work on this repo's existing plan — worth a quick dashboard check (Project Settings → Git) before committing to it in #239.

## 3. Confirming `services/server`'s preview deploy for the same commit

`on: workflow_run` can chain a workflow after `deploy-server-preview.yml` completes: activity types are `completed`, `requested`, `in_progress`, and success/failure is read via `github.event.workflow_run.conclusion` ([Events that trigger workflows — workflow_run](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows)). Like every trigger discussed here, **the triggered workflow file must exist on the default branch** for the trigger to fire (same page). The REST API's workflow-run object confirms a `head_sha` field is present on every run ([REST API — Get a workflow run](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28#get-a-workflow-run)), and by extension the `workflow_run` event payload carries the same run object, so `github.event.workflow_run.head_sha` is available to pin the e2e job to the exact commit that finished building — this part is reliable.

**What `workflow_run` success does _not_ guarantee, given how this repo's deploy job is written:** the `deploy` job in `deploy-server-preview.yml` runs on `[self-hosted, vps]` and only does `docker pull ... && ./scripts/infra.sh server-preview-up`, with **no health check and no verification that the running container matches the SHA that was just built** (per the workflow contents already confirmed in this repo). A green `workflow_run` conclusion tells you the SSH commands exited 0 — it does not tell you the service is actually listening and healthy, nor rule out a race with a second push landing mid-restart on this shared, overwritten environment. Given that, the e2e workflow should not treat `workflow_run: completed/success` as sufficient on its own; it should follow with its own smoke check (e.g. poll a `/health` or `/version` endpoint on the preview server and, if the service exposes one, compare a deployed-commit indicator to the target SHA) before running the suite. No Vercel or GitHub doc bears on this piece — it is purely a property of this repo's own deploy script, not something a primary source can confirm or deny.

## 4. Vercel REST API polling as a confirmation step for the console side

`GET /v7/deployments` is the current List Deployments endpoint and documents a `sha` query parameter — **`sha`**, not `gitSource.sha` — described as "Filter deployments based on the SHA," alongside `branch`, `projectId`, `target`, and `state` (one of `BUILDING, ERROR, INITIALIZING, QUEUED, READY, CANCELED, BLOCKED`) ([REST API — List deployments](https://vercel.com/docs/rest-api/deployments/list-deployments)). So a polling step is legitimate and precisely specified: `GET https://api.vercel.com/v7/deployments?projectId=<id>&sha=<commit-sha>&target=preview` with a bearer token, polling until a returned deployment's `readyState` is `READY` (or terminal-failing on `ERROR`/`CANCELED`). Note the documented `target` enum for the _response_ object only lists `production`, `staging`, or `null` — the docs do not show `"preview"` as a `target` value in the deployment object itself, so filtering by `target=preview` as a _query_ parameter should be verified against a live response before relying on it; filtering by `sha` alone (unambiguous per commit) sidesteps that uncertainty entirely.

**Compared to A/B/C:** polling is strictly more code (a loop with backoff, a token to manage, error handling) than reacting to `vercel.deployment.success`'s `repository_dispatch` payload, which already hands the workflow a ready URL for the exact SHA with no polling required. Given §2's finding that Vercel's native `repository_dispatch` is available at no infrastructure cost and already carries the SHA + ready URL, polling only earns its keep as a _fallback/verification_ layer (e.g., if the team wants a second, independent check that a URL is truly reachable before spending CI minutes on Playwright), not as the primary trigger.

## 5. The every-push-to-`dev` scoping question

Per §1 and the repo's existing `deploy-server-preview.yml` (which triggers `on: push` to `dev` with path filters, not `on: pull_request`), **both halves of "preview" already redeploy on every push to `dev`**, not per-PR: Vercel deploys a preview for any non-production-branch push by default ([Environments](https://vercel.com/docs/deployments/environments)), and the server side is wired the same way in this repo. Chaining the e2e workflow off either `repository_dispatch` (`vercel.deployment.success`, scoped by SHA) or `workflow_run` (chained off `deploy-server-preview.yml`, itself `on: push` to `dev`) inherits this: **the future e2e workflow will run once per push to `dev`, not once per PR.** That matches decision #230's framing of "the preview environment is the CI gate" for a _shared_ environment, but it is worth the requester flagging explicitly for #239/#227 whether that's the intended scope — e.g. whether rapid pushes to `dev` should queue/cancel-in-favor-of-latest e2e runs (mirroring Vercel's own build-cancellation behavior on the console side, [A Deployment for Each Push](https://vercel.com/docs/git/vercel-for-github#a-deployment-for-each-push)) rather than run the full suite on every intermediate commit.

---

## Recommendation

Trigger the e2e workflow (#239) on Vercel's native `repository_dispatch` events (`vercel.deployment.success`, filtered to `client_payload.git.ref == 'dev'`) — this needs no new infrastructure beyond the existing GitHub App integration and hands the job the exact commit SHA and live preview URL directly, matching Vercel's own recommended pattern over `deployment_status`. Combine this with a short readiness check at the start of the e2e job for the server side: either gate on `workflow_run` completion of `deploy-server-preview.yml` for the same SHA, or (more robustly, given that job has no health check of its own) poll the running service's own health/version endpoint before running Playwright, since a green deploy job on the self-hosted VPS runner does not by itself prove the service is live and matches that SHA. Skip Deploy Hooks (inbound-only, not applicable) and skip building a custom webhook relay (option B) — Vercel's native integration already provides that relay for free. Flag explicitly for #239/#227: because both preview pieces redeploy on every push to `dev` rather than per-PR, the e2e workflow as designed here will run on every `dev` push too — worth deciding intentionally (and possibly adding concurrency-cancellation) rather than inheriting it as an accident of how the two existing deploy paths are wired.
